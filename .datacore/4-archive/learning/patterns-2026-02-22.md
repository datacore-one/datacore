Approaches that work well. Agents reference this before tasks.

## DIP Inspector Validation Workflow

**Context**: Validating existing DIPs for compliance with system standards and catching bugs before they propagate.

**Pattern**: Use dip-preparer agent in validation mode to audit DIPs systematically:
1. Run inspector against existing DIP
2. Check structure (required sections: Rationale, Backwards Compatibility, Security Considerations, Open Questions)
3. Verify content consistency (spelling, terminology, format)
4. Validate integration with CLAUDE.md principles
5. Check alignment with other DIPs (related refs, compatibility)

**Why it works**: The inspector catches bugs that slip through (e.g., CANCELED/CANCELLED inconsistency) that could cause parser issues downstream. It also identifies template evolution (Agent Context format differs between old and new DIPs).

**Example**: Auditing DIP-0009 revealed CANCELLED vs CANCELED inconsistency (American vs British spelling) — fixed to match org-mode-conventions.md standard and core parser expectation.

**Source**: DIP-0009 implementation + validation, 2026-02-22

## DIP Submodule Git Workflow

**Context**: DIPs live in .datacore/dips/ as a git submodule. Changes must be properly committed at both levels.

**Pattern**:
1. Make changes inside .datacore/dips/ (e.g., edit DIP-0009.md)
2. Commit changes IN THE SUBMODULE: `cd .datacore/dips && git add . && git commit -m "..."`
3. Push submodule: `git push` (from inside .datacore/dips/)
4. Return to parent repo: `cd ../..`
5. Stage submodule commit ref: `git add .datacore/dips` (this updates parent's .gitmodules commit pointer)
6. Commit parent: `git commit -m "..."`
7. Push parent

**Why it works**: Submodules track a specific commit ref in the parent. If you commit in parent without committing/pushing in submodule, the submodule commit stays local. This creates state mismatch: CI/CD and collaborators see the old submodule version.

**Common mistake**: Forgetting to commit changes INSIDE the submodule before committing parent. Result: changes appear locally but fail in CI.

**Source**: DIP-0009 implementation, 2026-02-22

## Spelling Standardization: CANCELLED (British)

**Context**: System standardizes terminology for consistency. Org-mode conventions and core parser use CANCELLED.

**Pattern**: When standardizing across docs, reference the primary source (org-mode-conventions.md, the parser) and ensure all dependent files align. This prevents subtle bugs where different spellings are treated as different keywords.

**Why it matters**: Parser bugs from spelling mismatches are hard to debug. A TODO with `CANCELLED` status might not be recognized if code looks for `CANCELED`.

**Source**: DIP-0009 correction, cross-referenced org-mode-conventions.md, 2026-02-22

## DIP Template Evolution Tracking

**Context**: DIP templates and conventions evolve. DIP-0000 template is authoritative, but older DIPs may not conform.

**Pattern**: When updating an older DIP, check against:
1. DIP-0000 template (current standard)
2. Recent DIPs (DIP-0019, DIP-0022) for emerging conventions
3. Related DIPs for format consistency

**Notable evolution**: Agent Context section evolved from minimal to rich format with When to Reference, Quick Reference, Related Agents, Integration Points subsections (visible in DIP-0019, DIP-0022 vs earlier DIPs).

**Why it works**: Newer DIPs are better documented, making them better patterns for structure.

**Source**: DIP-0009 audit, comparing DIP templates, 2026-02-22

## Command Naming vs Implementation Reality

**Context**: DIPs sometimes document aspirational designs; reality evolves differently.

**Pattern**: When auditing command specs, validate against:
1. CLAUDE.md commands table (source of truth for current commands)
2. .datacore/commands/ directory (actual implementations)
3. demoted/ folder (commands that exist but aren't promoted)

**Example**: DIP-0009 Part 5 specified /gtd-daily-start and /gtd-daily-end. Actual implementation uses /today, /tomorrow, /wrap-up, /continue. Weekly/monthly reviews exist but are demoted.

**Why it works**: Prevents docs from diverging from reality. If someone reads DIP-0009 and tries to use /gtd-daily-start, they'll be confused.

**Action**: Update DIP-0009 to reflect actual command names and status.

**Source**: DIP-0009 validation, 2026-02-22

## Agent vs MCP Tool Decision Pattern

**Context**: Deciding whether a capability should be implemented as a sub-agent or an MCP tool. Sub-agents spawn a full model invocation with context setup. MCP tools are direct function calls with structured input/output.

**Pattern**: If the core operation needs no AI reasoning -- just script execution, parsing, and structured output -- it should be an MCP tool, not a sub-agent. The decision heuristic:

1. Does the operation require LLM judgment, synthesis, or natural language generation? -> **Agent**
2. Is it mechanical: run script, parse output, return JSON? -> **MCP tool**
3. Does it need to make multi-step decisions based on intermediate results? -> **Agent**
4. Is it a single deterministic transformation? -> **MCP tool**

**Why it works**: Sub-agents add spawn overhead (model invocation, context loading, prompt construction) for zero benefit when the work is mechanical. An MCP tool call is a direct function invocation -- faster, cheaper, more predictable.

**Example**: youtube-transcriber sub-agent was just wrapping a Python script call (`yt_transcriber.py`) with no AI reasoning. Converted to `transcribe_youtube` MCP tool. Spawn time went from seconds (model invocation) to milliseconds (direct script call).

**Anti-pattern**: Wrapping every script in a sub-agent "because agents are the pattern." Agents are for reasoning; tools are for execution.

**Source**: youtube-transcriber refactor (agent -> MCP tool), 2026-02-22

## MCP Tool Implementation Pattern in Datacore

**Context**: Adding a new MCP tool to a Datacore module.

**Pattern**:
1. Add tool definition to module's `tools/index.js`: zod schema for input, handler function
2. Handler uses `execSync` (or `execFileSync`) to call the underlying Python script
3. Parse script stdout as JSON, return structured result
4. Declare tool in `module.yaml` under `tools:` section with name, description, schema ref
5. No npm publish needed -- tools are dynamically imported from disk at runtime

**Key implementation details**:
- Use `execSync` with `{ encoding: 'utf-8', timeout: 120000 }` for script calls
- Wrap in try/catch, return error object on failure (don't throw)
- Python script path: resolve relative to module directory using `__dirname`
- Tool name convention: `module_name__tool_name` (double underscore namespace)

**Why it works**: Keeps the Python script as the single source of truth for the operation. The JS tool is a thin wrapper providing MCP protocol compliance. No code duplication.

**Source**: transcribe_youtube tool added to research module, 2026-02-22

## Agent Deprecation Pattern

**Context**: Replacing a sub-agent with a different mechanism (MCP tool, direct integration, etc.) while preserving history.

**Pattern**:
1. In agent definition file frontmatter: add `status: deprecated` and `deprecated_by: [replacement]`
2. In registry (`registry/agents.yaml`): add same `status: deprecated` and `deprecated_by` fields
3. In parent agent that spawned it: remove from `spawns:` list, add replacement to `uses_tools:` (or equivalent)
4. **Keep the agent file** -- do not delete. It serves as documentation of what existed and why it was replaced.
5. Update any routing logic (e.g., knowledge-extractor) to use the new mechanism

**Why it works**: Clean deprecation trail. Anyone reading the old agent file immediately sees it's deprecated and what replaced it. Registry queries can filter by status. No broken references from old docs or logs pointing to deleted files.

**Common mistake**: Deleting the agent file. This breaks historical references and loses context about why the agent existed.

**Source**: youtube-transcriber agent deprecated in favor of transcribe_youtube MCP tool, 2026-02-22

## Shell Script Word-Splitting on Filenames with Spaces

**Context**: Pre-commit hooks or shell scripts iterating over file lists that may contain spaces in paths.

**Pattern**: When iterating over a list of filenames from `git diff --cached --name-only` (or similar), set `IFS` to newline before the loop:

```bash
# Bad: word-splits on spaces in filenames
for file in $staged; do ...

# Good: only split on newlines
OLD_IFS="$IFS"
IFS=$'\n'
for file in $staged; do ...
done
IFS="$OLD_IFS"
```

**Why it works**: Default `IFS` includes space, tab, newline. A filename like `My Document.md` becomes two iterations: `My` and `Document.md`. Setting IFS to newline-only ensures each line (one filename) is one iteration.

**Alternative**: Use `while read` with process substitution: `git diff --cached --name-only | while read -r file; do ... done` -- but note this runs in a subshell so variable changes won't propagate.

**Source**: Pre-commit hook fix for filenames with spaces, 2026-02-22
